## 2. AI 활용 원칙

저는 AI를 ‘대신 만들어 주는 도구’가 아니라 ‘초안을 빠르게 받고, 제가 검증하는 협업 도구’로 사용했습니다.

| 구분 | 제가 직접 한 일 | AI에게 맡긴 일 |
| --- | --- | --- |
| 기획 | 목표와 기술 스택 설정, 레퍼런스 UI 선정, 차별화 방향 결정 | 모델 후보 비교, 기능 제안 |
| 디자인 | 화면을 보고 ‘밋밋하다’, ‘구조가 다르다’ 등 피드백, 최종 채택 | 레이아웃·CSS 초안 |
| 개발 | 코드 일부 직접 입력, 적용, 파일 구조 정리, 로컬 서버 실행 | FastAPI·React 코드 작성 (Claude) |
| 검증·디버깅 | 오류 화면·터미널·콘솔·Render 로그를 캡처해 원인 확인, AI 답변의 오류 지적 | 로그를 해석해 오류 원인을 찾고 해결 방법 제시 (Claude) |
| 배포 | Render 배포·환경변수 입력·재배포, HuggingFace 토큰 발행 | 설정값 안내 (Claude), GitHub 커밋·풀 (Codex) |
| 포트폴리오 반영 | 문구·이미지·구성 결정 | Codex로 사이트 코드 반영 |

도구별 역할: Claude는 코드 작성과 오류 해결, Codex는 GitHub 커밋·풀을 맡았습니다. 코드 일부 직접 입력, Render 배포, HuggingFace 토큰 발행은 제가 직접 했습니다.

**제가 지킨 4가지 원칙**

1. 요구는 구체적으로 한다. 기술 스택, 대상(초보자), 원하는 결과를 먼저 정하고 요청했습니다.
2. AI 코드는 반드시 실행해서 확인한다. 화면, 터미널, 브라우저 콘솔, Render 로그로 검증했습니다.
3. 오류는 추측하지 않고 근거를 함께 전달한다. 캡처와 로그를 붙여서 물었습니다.
4. AI의 답이 틀리거나 요구와 다르면 지적하고 방향을 바로잡는다.

## 4. 프롬프트 사례

실제 대화의 요지를 정리한 것입니다.

**① 초기 요청 — 조건을 한 번에 제시**

> 첨부한 구조(React + Vanilla CSS / Python + FastAPI / HuggingFace / Render)대로 하고, 다국어 모델을 추천해 달라. 평범하지 않게, 초보자가 순서대로 따라 할 수 있도록 상세하게.

**② 피드백형 — 레퍼런스를 근거로 방향 전환**

> 보통의 챗봇 UI는 이렇다며 레퍼런스 스크린샷을 첨부하고, 지금 코드와 구조가 너무 다르니 이 화면을 참고해 수정해 달라. 토큰은 적당히 쓰고, 다른 챗봇과 차별화되게 해 달라.

이 한 번의 요청이 v3의 구조 변경, 사용량 제한, 포트폴리오 가이드 모드로 이어졌습니다.

**③ 오류 전달형 — 캡처와 함께 한 줄로**

> (Render 빌드 로그 캡처) 왜 이런 거야?

로그가 근거라서 원인(루트 디렉터리 설정 누락)을 바로 찾을 수 있었습니다.

**좋은 요청의 공통점:** 결과물의 기준(레퍼런스), 제약(토큰·초보자), 근거(캡처·로그)가 함께 있었습니다.

## 5. AI의 결과를 검증하고 바로잡은 사례

| 상황 | 문제 | 제가 한 확인 | 결과 |
| --- | --- | --- | --- |
| 무료 사용량 소진 | 화면에 한도 소진 오류. 당시 모델이 32B였고, AI가 선택지로 안내했던 크기였음 | 오류 화면과 모델 표시 확인 | 8B로 고정하고, 호출 제한·답변 저장·기록 제한을 설계 (사용량이 빨리 닳은 원인 중 하나로 추정) |
| Render 빌드 실패 | requirements.txt를 찾지 못함 | 로그 캡처로 확인 | Root Directory를 backend로 설정 |
| Render 실행 실패 | `No module named 'openai'` | 로그 맨 아래 오류 확인 | requirements.txt에 추가 후 성공 |
| 화면은 뜨는데 연결 안 됨 | 요청 주소에 슬래시가 두 개(`//api/health`)로 404 | F12 콘솔의 요청 주소 확인 | 환경변수 끝 슬래시 제거 |
| AI의 답 번복 | requirements.txt를 교체하라던 AI가, 제가 ‘다 지우면 안 되지 않냐’고 묻자 전체 목록을 보고 ‘그대로 두는 게 안전’으로 정정 | 의문을 제기해 검증 | 근거 없는 단정을 질문으로 바로잡음 |
| AI의 추정 오류 | ‘연결 안 됨’ 화면을 AI가 포트폴리오 위젯으로 추정 | Render에서 본 화면이라고 정정 | 원인 추적을 다시 시작 |
| 요구 오해 | 코드 구분선 요청을 AI가 주석 배너와 에디터 설정으로 오해 | 원하는 결과를 예시 캡처와 함께 재설명 | 요구대로 반영 |

이 과정에서 AI도 틀릴 수 있다는 점, 그리고 로그와 실행 결과가 가장 믿을 수 있는 근거라는 점을 배웠습니다.

## 6. 설계 결정

| 결정 | 이유 |
| --- | --- |
| Qwen3-8B 사용 | 다국어 지원, 무료 구간에서의 속도와 사용량 |
| 레퍼런스 UI 구조 채택 | 사용자가 익숙한 챗봇 구조 |
| 포트폴리오 가이드 모드 | 방문자가 제 프로젝트를 질문할 수 있고, 프로필에 없는 내용은 지어내지 않도록 제한 |
| 사용량 절약 정책 | 사용자당 시간당 12회, 서버 하루 200회, 대화 기록 8개와 글자 수 제한, 응답 길이 선택 |
| 같은 첫 질문의 답변 저장 | 추천 질문은 AI를 다시 호출하지 않음 |
| 에너지 미터 | 한도를 숨기지 않고 화면에 보여 줌 |
| 음성 입력·읽어주기 | 브라우저 내장 기능이라 AI 사용량을 쓰지 않음 |
| 언어 감지 배지 | 글자 종류로 판단해 서버 호출 없이 표시 |

## 7. 보안과 운영

- HuggingFace 토큰은 `.env`와 Render 환경변수로만 관리하도록 구성했습니다. (`.gitignore` 적용, 업로드 전 `git status`로 확인)
- 백엔드는 허용한 주소(CORS)에서 온 요청만 받습니다.
- 메시지 길이, 대화 기록, 요청 횟수를 서버에서 제한합니다.
- 오류 문구에는 내부 정보를 노출하지 않습니다.

## 8. 한계와 배운 점

**한계**

- 무료 서버는 15분 이상 쓰지 않으면 잠들어 첫 접속이 느립니다.
- 무료 AI 사용량에는 한도가 있어, 한도가 차면 답변하지 못합니다.
- 언어 감지는 글자 모양만 보기 때문에 악센트 없는 스페인어 등은 영어로 표시될 수 있습니다.
- 음성 인식은 브라우저에 따라 지원 여부가 다릅니다.

**배운 점**

- AI의 결과는 초안이며, 실행 결과와 로그로 검증해야 합니다.
- 오류는 캡처와 로그를 함께 전달하면 원인 파악이 훨씬 빠릅니다.
- 무료 자원은 한도를 전제로 설계해야 합니다.
- 배포 오류를 브라우저 콘솔, 터미널, Render 로그 순서로 좁혀 가며 원인을 찾는 방법을 익혔습니다. AI가 제안한 해결책도 그대로 따르지 않고 실행 결과로 확인하는 습관이 생겼습니다.
